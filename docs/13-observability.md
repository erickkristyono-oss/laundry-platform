# 13 — Observability

Scope: baseline conventions every service (Identity, Core, Payment, Notification, Reporting) and the Gateway must implement identically, so logs/metrics/traces are correlatable across service boundaries despite each service owning its own database and deploy lifecycle. Concrete instrumentation (which OTel SDK version, which Grafana dashboards) is a Phase 1 implementation task — this document fixes the *contract*, matching the Phase 0 spec's architecture-only scope.

## 1. Structured Logging

- All logs are structured JSON (one object per line), never free-text `printf`-style logs, so they are queryable in a centralized log store.
- Minimum fields on every log line: `timestamp`, `level`, `service`, `message`, `request_id`, `correlation_id` (when applicable), `trace_id`/`span_id` (when applicable).
- No PII beyond what §12 of `12-security-baseline.md` allows (masked phone/email); no secrets, tokens, or password hashes ever logged.
- Log levels: `DEBUG` (dev only, verbose), `INFO` (state transitions, requests), `WARN` (recoverable anomalies, e.g., a retried outbox publish), `ERROR` (failed operations needing attention), `FATAL` (process cannot continue).

## 2. Request ID

- Generated by the Gateway for every inbound HTTP request (`X-Request-ID`, UUID) if the client didn't supply one; propagated unchanged to the downstream service and echoed back in the response header and in the error envelope (`11-error-handling.md` §1).
- Purpose: trace one HTTP call end-to-end through Gateway → Service → (any synchronous downstream call it makes).

## 3. Correlation ID

- A **correlation ID** is broader than a request ID: it ties together an entire *business operation* that may span multiple HTTP requests and asynchronous events — e.g., "create order #123" → the `POST /orders` request, the `order.created` event, the notification it triggers, and the reporting projection update it eventually causes all carry the same `correlation_id`.
- Generated once at the origin of a business operation (typically = the first request's `request_id`, promoted to a `correlation_id`) and propagated: HTTP → outbox event envelope (as an additional envelope field alongside `event_id`, not replacing it) → consumer logs.
- This lets an operator search one ID and see the entire cross-service story of a single order/payment/refund, which is essential given the system has no single database to `JOIN` across.

## 4. Event Correlation ID

- Every event in `08-event-contract.md` §2's envelope gains one additional field for this purpose: `correlation_id` (alongside the already-specified `event_id`, which identifies *this specific event*, not the broader operation).
- Consumers log `correlation_id` on every line related to processing that event, so a Notification or Reporting failure can be traced back to the originating order/payment action without re-deriving it from `aggregate_id` chains.

## 5. Metrics

Exposed in Prometheus exposition format at `/metrics` on each service (internal-network only, not via the Gateway).

| Category | Example metrics |
|---|---|
| HTTP (Gateway + services) | `http_requests_total{service,route,method,status}`, `http_request_duration_seconds{service,route}` |
| Outbox health | `outbox_pending_count{service}`, `outbox_oldest_pending_age_seconds{service}`, `outbox_publish_failures_total{service}` |
| Event consumption | `event_consume_total{service,event_type,result}`, `event_consume_lag_seconds{service,event_type}` |
| Business (via Reporting projections, exposed for dashboards, not alerting) | `orders_created_total{outlet_id}`, `orders_completed_total{outlet_id}`, `payments_paid_total{outlet_id}`, `refunds_completed_total{outlet_id}` |
| Database | connection pool utilization, query duration histograms (via `pgx` instrumentation) |
| Cache | Redis hit/miss ratio per key namespace |

## 6. Health, Readiness, and Liveness Checks

| Endpoint | Purpose | Checks |
|---|---|---|
| `GET /healthz` (liveness) | Is the process alive at all? | Process responds; no external dependency checks (a slow DB must not make Kubernetes/Compose kill a healthy process) |
| `GET /readyz` (readiness) | Can this instance currently serve traffic? | DB connection pool reachable, RabbitMQ connection open, (Redis reachable where required for correctness, e.g., rate limiting at the Gateway) |
| `GET /metrics` | Prometheus scrape target | N/A (not a health check, listed here for co-location) |

Every service and the Gateway expose all of the above; orchestration (Docker Compose healthchecks in Phase 1, Kubernetes probes later) wires liveness → restart policy and readiness → load-balancer inclusion.

## 7. Distributed Tracing

- OpenTelemetry-compatible tracing: every inbound HTTP request at the Gateway starts a trace (`trace_id`); every synchronous service-to-service call (e.g., Payment → Core for order-total verification) continues that trace as a child span, propagated via the W3C `traceparent` header.
- Outbox-relayed events are **not** part of the same synchronous trace (they're asynchronous by design) but carry `correlation_id` (§3) as the mechanism to reassociate them during investigation; a span link (OTel's `SpanContext` link, not a parent-child edge) from the consumer's processing span back to the producer's publish span is the recommended Phase 1 enhancement once an OTel collector is in place.
- Spans are named consistently: `{service}.{operation}` (e.g., `payment.create_payment`, `core.finalize_weighing`).

## 8. Alerting Thresholds (baseline, tunable in Phase 1)

| Signal | Threshold | Severity |
|---|---|---|
| `outbox_oldest_pending_age_seconds` | > 300s | Warning — relay may be stalled |
| `outbox_oldest_pending_age_seconds` | > 900s | Critical — events not reaching consumers |
| `readyz` failing | > 30s | Critical — instance pulled from rotation |
| `http_request_duration_seconds` (payment endpoints, p99) | > 2s | Warning |
| `event_consume_lag_seconds` (any consumer) | > 60s | Warning |

## 9. Summary Table

| Concern | Mechanism |
|---|---|
| Structured logging | JSON logs, common field set, no secrets/raw PII |
| Request correlation | `request_id` (per HTTP call) |
| Business-operation correlation | `correlation_id` (per business operation, spans requests + events) |
| Event correlation | `correlation_id` field added to the event envelope |
| Metrics | Prometheus `/metrics`, HTTP + outbox + event + business + DB + cache |
| Health | `/healthz` (liveness), `/readyz` (readiness) |
| Tracing | OpenTelemetry, W3C traceparent propagation, `{service}.{operation}` span naming |
| Dashboards | Grafana, sourced from Prometheus + (optionally) the Reporting read models for business metrics |
